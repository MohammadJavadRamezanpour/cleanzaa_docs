# Stripe Payments and Invoicing integration plan

**Status:** Implementation proposal for synthetic development and Stripe sandbox review, 2026-11-10. This is based on Cleanzza's approved product direction, Stripe's published guidance, and the installed Stripe skills. The Stripe `stripe_implementation_planner` call did not return a guide, so this is not planner output. This plan does not approve real quote acceptance, payments, transfers, or fiscal documents.

## Current state and chosen direction

Cleanzza is a Milan marketplace for Home Cleaning, Car Wash, and Pet Care. The application uses a FastAPI backend, Next.js frontend, and PostgreSQL. It currently exposes draft quotes with `acceptance_ready: false` and draft-only orders. A [developer-only synthetic Stripe Checkout experiment](../features/stripe-sandbox-checkout.md) now exists; there is no public payment API, webhook handler, Connect onboarding, or invoicing implementation.

[ADR 0006](../adr/0006-phase-1-payment-direction.md) chooses one EUR card charge to the platform at booking and a separate transfer to the assigned worker after customer confirmation or an authorized support resolution. The worker is unknown when checkout starts. The 20% platform / 80% worker split is provisional; tax and invoice treatment may change it. Stripe's [separate charges and transfers guide](https://docs.stripe.com/connect/separate-charges-and-transfers.md?platform=web&integration=checkout&ui=stripe-hosted) supports this payment pattern in Italy, but does not approve Cleanzza's specific account, legal role, or transfer timing.

## Build sequence

1. **Define the accepted financial contract.** Obtain the written Italian tax/legal and Stripe account decisions in the [review checklist](italy-tax-stripe-review-checklist.md). Define the legal supplier, invoice issuer, VAT treatment by service and fee, cent allocation, refund corrections, connected-account configuration, and liability. Amend ADRs 0004/0006 and API contracts if the reviewed model differs. Until then, keep real acceptance and payment disabled.
2. **Build the synthetic order and money model.** Version and freeze accepted quote lines, tax fields, gross total, platform share, worker amount, and currency. Keep payment, refund, transfer, payout, and fulfillment states separate. Test PostgreSQL constraints, concurrency, and idempotent retries with a fake provider. Do not fill unknown tax fields with zero.
3. **Add sandbox checkout.** After the account and restricted sandbox API key are provisioned, use a server-created, Stripe-hosted Checkout Session for one on-session EUR charge. Associate it with Cleanzza's immutable quote/order attempt and a stable provider idempotency key. Keep the order private and payment-pending until verified capture; a success redirect is only a display path. Do not pass `application_fee_amount` or a destination account for separate charges and transfers. Do not enable `automatic_tax` before the tax-liable entity and active registration are verified.
4. **Add signed webhooks and reconciliation.** Verify the raw request body with the webhook signing secret before parsing events. Persist provider event IDs and financial movement IDs with unique constraints, acknowledge only after durable recording, process duplicate and out-of-order events safely, and reconcile against Stripe periodically. Handle Checkout completion and asynchronous success/failure, payment/refund/dispute, Connect capability, transfer, and payout outcomes as the approved flow requires. Matching starts only after capture is confirmed. Stripe says [webhooks are required for reliable Checkout fulfillment](https://docs.stripe.com/checkout/fulfillment.md?ui=full-page).
5. **Add worker onboarding and settlement.** Use Stripe-hosted Connect onboarding and store only opaque account IDs and capability status. Select the exact Accounts v2 configuration with Stripe's account-specific approval. Before transfer, recheck the connected account's transfer capability and the Cleanzza confirmation/support decision. Calculate the approved worker amount from the frozen snapshot, use provider idempotency, and record transfer, reversal, and later bank payout as separate movements. Restricted or failed accounts remain payable for operations review. Never label a transfer as a completed bank payout.
6. **Choose the invoice/document route after adviser review.** Stripe can issue a receipt or a paid invoice for a one-time Checkout payment, but that does not establish whether the document meets Cleanzza's Italian fiscal obligations. If the approved issuer and document requirements fit Stripe's [paid invoice receipt](https://docs.stripe.com/receipts.md#paid-invoice-receipts), enable Checkout's post-payment invoice creation and reconcile `invoice.paid` to the existing charge. Otherwise, integrate the approved fiscal or electronic invoicing process and store its document reference. Use [Stripe Invoicing](https://docs.stripe.com/invoicing) for a distinct amount owed to a named customer only if the approved flow calls for it; do not create a second charge for the booking already paid at Checkout. Specify credit notes or corrections for refunds and disputes before enabling document issuance.
7. **Add operations and release controls.** Provide an auditable view for failed charges, refunds, disputes, restricted accounts, unpaid transfers, and reconciliation gaps. Alert the duty owner and document retry/manual resolution. Keep a hard production gate on quote acceptance, order submission, live Stripe keys, and payment endpoints until the [external approval record](phase-1-external-approval-record.md) is signed and the required CI, migration, OpenAPI, contract, and hosted sandbox checks pass.

## Sandbox verification

Use synthetic identities and Stripe test payment methods only. Cover a EUR 40.00 booking, SCA challenge, delayed success/failure, duplicate and reordered webhooks, idempotent checkout retry, cancellation/full refund before work, post-start partial refund decision, dispute, transfer reversal, unavailable worker capability, failed payout, reconciliation recovery, and mixed-service cent reconciliation. Assert that no worker offer is created before captured payment and no transfer occurs before customer confirmation or support authorization.

## Credentials and access

The Codex MCP OAuth connection currently grants read access to a Cleanzza sandbox; it is separate from backend API credentials. Use a least-privilege **restricted sandbox API key** for the FastAPI server and a sandbox webhook signing secret when webhook work begins. Store both in a local ignored secret file or a deployed secrets vault, never in Git, frontend code, logs, or chat. Use separate credentials for local development, CI, staging, and production. Decide exact permissions from the implemented API calls and test them in the sandbox before creating any live key.

## Open decisions

- Italian legal supplier, contracting parties, invoice/receipt issuer, B2C/B2B document requirements, and any Sistema di Interscambio process.
- VAT treatment for each service and platform/worker supply, registration and tax liability, exact line allocation, and refund/credit-note handling.
- The actual Italian Stripe platform's approval for separate charges and transfers, connected-account API/configuration, permitted transfer timing, fees, negative balances, and refund/chargeback funding.
- Approved customer/worker terms and the signed operational go/no-go review.

These decisions are tracked in the [external approval record](phase-1-external-approval-record.md). A sandbox walkthrough or API key alone does not clear them.
