# Support case intake

## Purpose and current scope

The Phase 1 support foundation lets a signed-in customer or cleaner record a general service, payment, safety, or other concern without a Before Photo, special guarantee, or 24-hour deadline. It stores the case and an attributed creation event. The creator can list their own cases. A separately allowlisted administrator can see a redacted case queue and open a case detail with an audited read. This slice has no case attachments, order link, response, resolution command, notification, or frontend screen yet. It does not promise live support or an emergency response. Those are separate delivery and operating requirements in [ADR 0008](../adr/0008-phase-1-boundaries-and-support.md).

`SUPPORT_CASES_ENABLED` defaults to `false`. Production configuration rejects `true` while the retention and legal-hold process, staffing and response workflow, escalation path, and customer wording are unresolved. Controlled local or staging tests use synthetic descriptions. `SUPPORT_REVIEWER_USER_IDS` defaults to an empty JSON list of UUIDs and must explicitly name the mapped Auth0 admin users permitted to inspect cases in those tests. General administrators are denied. The flags do not clear any launch gate in [ADR 0008](../adr/0008-phase-1-boundaries-and-support.md) or [ADR 0002](../adr/0002-phase-1-personal-data.md).

## API contract

`POST /support/cases` requires a valid customer or cleaner session cookie, matching `X-CSRF-Token`, an allowed `Origin` when supplied, and `Idempotency-Key` (1–128 characters). The JSON body has exactly `creator_role` (`CUSTOMER` or `CLEANER`), `category` (`SERVICE`, `PAYMENT`, `SAFETY`, or `OTHER`), and `description` (10–2000 characters after trimming). The requested role must be present in the authenticated user's roles. A user with both roles chooses which role the case represents. No order ID, file, contact detail, payment instruction, or requested remedy is accepted in this slice.

The response is `201` with `id`, `creator_role`, `category`, `description`, `status: "OPEN"`, and an explicit-offset ISO 8601 `created_at`. Retrying the same key and normalized body for the same user returns the original `201` response. Reusing the key with different content returns `409 CONFLICT`. Missing or invalid authentication returns `401 UNAUTHENTICATED`; role mismatch or failed CSRF/origin check returns `403 FORBIDDEN`; malformed or extra fields, invalid category, missing key, or an invalid description return `422 VALIDATION_ERROR`. When the feature is disabled or no database session is configured, the endpoint returns `503 SERVICE_UNAVAILABLE`.

`GET /support/cases` requires a valid customer or cleaner session and returns only that user's cases, newest first, as `{ "items": [...], "next_cursor": UUID | null }`. Optional `cursor` is a case UUID from a previous page and must belong to the same user; another user's or an unknown cursor returns `404 NOT_FOUND`. Optional `limit` defaults to 20 and permits 1–50. The response uses `Cache-Control: no-store`; there is no cross-user case search. Both endpoints use the shared safe error envelope. They expose no payment or order state changes.

`GET /admin/support/cases` requires an Auth0 admin bearer token with valid signature, configured audience and client, MFA claim, mapped user, database `ADMIN` role, and explicit inclusion in `SUPPORT_REVIEWER_USER_IDS`. It returns newest-first `{ "items": [...], "next_cursor": UUID | null }`. Each queue item has `id`, `creator_role`, `category`, `status`, and `created_at`; description and creator ID are omitted. Optional `cursor` must reference an existing case or returns `404 NOT_FOUND`; `limit` defaults to 20 and permits 1–50. `GET /admin/support/cases/{case_id}` uses the same authorization, returns the case fields plus `creator_user_id`, and writes a `VIEWED` event with the reviewer ID in the same transaction before returning. An unknown ID returns `404 NOT_FOUND`. Both responses use `Cache-Control: no-store`. Missing/invalid auth is `401 UNAUTHENTICATED`, an authenticated admin outside the support allowlist is `403 FORBIDDEN`, invalid parameters are `422 VALIDATION_ERROR`, and a disabled feature or missing database session is `503 SERVICE_UNAVAILABLE`. These endpoints do not assign, reply to, or close a case.

## Persistence and safety

Migration `0013_support_case_intake` adds `support_cases` and `support_case_events`. A case references the creating user and records role, category, description, OPEN status, idempotency key, request fingerprint, and server timestamp. PostgreSQL checks constrain the role, category, OPEN-only status, and description length. A unique `(creator_user_id, idempotency_key)` constraint and transaction-scoped advisory lock make duplicate creation safe; the creation event is in the same transaction. The event references the case and actor and uses a server timestamp. Migration `0014_support_case_review` expands the event check to permit `VIEWED` for audited staff detail reads. Future case actions must expand the state and event constraints in a reviewed migration.

Descriptions may contain sensitive personal information. They are not logged by the request logger or returned to other users. Staff queue rows omit descriptions; an allowlisted detail read records the actor. The schema uses restricted foreign keys until the approved export, retention, deletion, and legal-hold rules are implemented. Do not drop these tables after real cases exist without a data-preservation decision. Staff viewing is not an outcome: a populated case cannot yet be treated as operationally handled.
