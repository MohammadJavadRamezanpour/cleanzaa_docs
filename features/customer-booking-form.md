# Customer booking form (B10)

## Implemented form

The mobile-width `/book` page loads the typed `GET /catalog/launch` response and presents shared booking inputs: one or more of the three launch services, service date, start time, fixed Milano area, street, house number, CAP, and recipient type. It provides loading, failure/retry, and ready states, with explicit labels for keyboard and assistive technology. The page is linked from `/services`; its 440-pixel frame also applies on desktop. Dates and times are entered for the catalog's `Europe/Rome` timezone. The city and area are controlled values from the server catalog, not arbitrary customer text.

Each selected service gets 1–8 whole-hour duration and explicit yes/no choices for worker equipment and supplies. Home Cleaning additionally asks for beginner/professional level, rooms or areas as text, and a positive room count. Car Wash asks for make/model. Pet Care asks for dog/cat and breed. For a service for someone else, the form asks for that person's first name, last name, and phone. The `Check details` action runs client-side validation for the required fields and Milano CAP range and displays field and service errors. Editing any field clears a previous validation result. The browser does not claim worker availability or exact street boundary coverage from these checks.

The form keeps address, recipient, and schedule values in browser component state only. Once a selected service has 1–8 hours and the CAP is in the Milano range, the form requests a draft price from `POST /quotes/drafts` using only area code, city, CAP, service codes, and hours. It waits 300 ms after an edit so typing a postcode does not produce a request per keystroke. The backend remains authoritative for the gross EUR total and lines. The form shows a loading state, line totals, expiry in `Europe/Rome`, an error with a retry action, and a notice when a newly calculated total differs from the previous displayed total. Service, duration, and CAP edits immediately hide the previous preview. Older responses are ignored after those inputs change. An expired preview is removed and requires refresh; its 15-minute window never acts as quote acceptance.

The booking gate remains visible. The `Check details` action validates the local form but sends no request or order. Customer activation checks, accepted quote snapshots, and order creation are not implemented here; B11 will own the server-side order command after its legal/payment gates are cleared. No account, worker availability, exact street coverage, or accepted quote is inferred from local fields or the draft preview. The public service-page preview also remains available at `/services` as documented in [pricing-quotes.md](pricing-quotes.md).

## Contract and verification

This slice uses the existing public catalog and quote APIs and pinned generated TypeScript types. It adds no backend endpoint, OpenAPI change, database migration, idempotency key, audit event, or asynchronous effect. The quote API is public and read-only; its validation and `422`/`503` behavior are documented in [pricing-quotes.md](pricing-quotes.md). The frontend does not decide booking eligibility; a future backend order endpoint must validate location, inputs, quote, ownership, and account activation. The form does not store address or recipient data across reloads or send those values to the quote endpoint. Pure tests cover booking fields and the quote request's narrow data contract. From `front/`, run `npm run lint`, `npm run format:check`, `npm run typecheck`, `npm test`, `npm run contract:check`, and `npm run build`. Review `/book` in a browser at phone width and on desktop.

The product inputs and area rules are in [ADR 0003](../adr/0003-phase-1-launch-services.md). The quote and legal gates are in [ADR 0004](../adr/0004-phase-1-pricing-direction.md) and [ADR 0006](../adr/0006-phase-1-payment-direction.md).
