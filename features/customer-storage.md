# Customer storage (B03, first checklist item)

## Purpose and scope

This step adds the backend persistence boundary for a customer record. The
`customers` table initially held an application-generated UUID and a creation
timestamp. Revision `0002_customers` collected no personal data while D5 was
open. The later auth slice stores verified phone contact in `users`, under
[ADR 0002](../adr/0002-phase-1-personal-data.md).

Registration, contact verification, sessions, roles, profile fields, and HTTP
endpoints are separate B03 checklist items. The later authentication slice adds
the shared `users` relationship; see [customer-authentication.md](customer-authentication.md).

## Database contract

Alembic revision `0002_customers` created:

| Column | Type | Rule |
| --- | --- | --- |
| `id` | UUID | Primary key, required; generated by the application |
| `created_at` | Timestamp with time zone | Required; defaults to database current time |

Revision `0003_customer_auth` later adds nullable, unique `user_id` to link new
verified accounts without rewriting any earlier minimal records.

There is no mutable customer profile field yet. The repository provides
`create_customer(session)` and `get_customer(session, customer_id)`. Creation
flushes the row so its generated timestamp is available, but it does not commit;
the caller owns the transaction. A missing ID returns `None`. The primary key
prevents duplicate IDs.

The migration is additive and does not modify existing tables. A downgrade
drops `customers`; it is safe only before customer rows exist. Once registration
uses the table, production rollback must use a forward fix or a reviewed data
preservation plan. No asynchronous effect or external provider is involved.

## Privacy and pending decisions

The original migration held only an opaque ID and creation time. The approved
Phase 1 data direction is in ADR 0002; the auth slice defines the `users`
relationship and phone handling. No endpoint exposes the storage table itself.

## Verification

From `back/`, apply migrations to a PostgreSQL test database with
`.venv/bin/alembic upgrade head`, then run
`.venv/bin/pytest -q tests/test_customer_repository.py` with
`DATABASE_URL` set. The integration tests verify the actual table shape,
persistence across sessions, and caller-controlled rollback. Run the backend
canonical lint, format, type check, full test suite, and OpenAPI check before
delivery.
